## 5. Notes

- **Legacy slice:** `logistics/load-builder.html` lines 473–1078 (from `const TRAILER_TYPES = {` up to, not including, `function groupCartByZone(cart) {`), run in a `node:vm` context with a self-returning `Proxy` for `document`/`window` and a no-op `localStorage`. No further stubs were needed. The HTML is never edited.
- **`state` stub:** the slice declares its own `let state = {…}` (including `autoDownsize: true`), so the prompt's stub `{ forcedMode: false, forcedTrailers: [], runnerHeight: 0 }` is assigned over it after the slice loads. With `autoDownsize` therefore falsy, legacy's last-trailer 26ft-box-truck downsize is skipped — matching v2, whose `DEFAULT_PACK_OPTIONS.autoDownsize` is `false`. Both engines thus report every trailer as a 53ft Standard.
- **Row order:** v2 rows are emitted in ascending `posFromFront` (0 = nose) — confirmed on every run. Legacy rows carry `posFromFront = curX` from the same origin (pass-1 rows, then pass-2 remainder rows appended behind them) — also ascending on every run. The harness sorts both by `posFromFront` ascending, so row 1 is the nose and the last row is at the doors; columns are sorted by `posY`.
- **SKU coercion:** fixture SKUs pass through a verbatim copy of `jobPull.ts`'s `coerceSku` (it is not exported) before either engine runs; legacy receives the same coerced list.
- **`unplaced`** is Σ cart qty − Σ placed layer counts, which covers both v2's `balance` and legacy's "could not be placed" warnings.
- **`seqViolations`** groups each row's columns by the base layer's stated catalog L×W (footprint family) and compares adjacent rows that hold that family; `truckLB` uses stated L×W only (no rotation) and is `n/a` for multi-footprint carts.
- **`mixedLB`** is a stub (`n/a`) — lbr-02 adds the exact optimizer.
- **Like-for-like trucks:** on the 135 jobs where neither engine leaves pieces unplaced, v2 uses fewer trucks than legacy on 10, more on 18, the same on 107 (Σ 235 v2 vs 227 legacy). The raw Σ trucks / Σ unplaced totals in section 1 are skewed by the outliers in section 3.
- **`allowRotation` divergence (surprising):** on 34 jobs v2 leaves non-Holey SKUs unplaced because their catalog L×W×H has `allowRotation: false` and doesn't fit upright (e.g. 144"-long pieces stated with 144 as height). Legacy `buildDemand` always tries all six orientations for non-Holey parts regardless of the flag. This is a catalog-data and parity question for lbr-02 or the parts library, not something this harness changes.
- **Legacy never tops off:** legacy produced 0 mixed stacks across all 172 jobs. Pass 1's `buildColumn` hard-codes `shouldMix = false` and builds each size's remainder as a short pure stack (`maxBase = min(remaining, floor(H / h))`), so pass 2's remainder consolidation is left with nothing to mix on these carts.
- **Golden v2 vs the sandbox:** the Orchestrator's sandbox reported v2 at 51 of 52 mixed stacks on this piece set; the harness measures 29 of 52 (cross-checked against `plan.mixedStacks` and the per-column `mixed` flag, which agree). The truck count (1) and the "thinnest at the nose" shape match. The gap is not explained here (a different engine revision or counting method is possible); lbr-02 should gate on this harness's number.
